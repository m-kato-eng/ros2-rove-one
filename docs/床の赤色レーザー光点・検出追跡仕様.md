# 床の赤色レーザー光点・検出追跡仕様

作成日：2026-11-08。対象：Raspberry Pi 4 / Logitech C310。
本書はユーザー指定の追尾対象に合わせた**実装予定の仕様**。レーザー専用認識器への切替はまだ行っていない。
従来の広い明部・ライト照射領域ではなく、床に照射された赤色レーザーの小さな光点を対象にする。

## 1. 前提と確認済みの範囲

- 地面は平坦・水平。画像中央を水平線、下半分を地面と仮定する。
  動作前にPC画像中央の赤線と実際の水平線を、カメラ取付の手動調整で合わせる。
- 使用する照射点は1つ。レーザー本体・壁や空中の光源は対象にしない。
- 現在の320×240映像では、床の小さな光点とその移動を目視確認できた。
  表示上は白っぽく見えたが、赤成分の強さ・実際の画素数・白飛びは元JPEGで未評価。
  「赤色として安定識別できた」「自動追跡できた」という実測結果はまだない。
- 画像下半分は地面という運用上の仮定であり、単眼画像から高さを確認した結果ではない。

## 2. ノードの役割

|ノード|役割|
|---|---|
|camera_capture|カメラJPEGと入力stampを提供する|
|object_recognition|赤い光点候補を検出し、画像内での同一候補の位置を追跡。座標・有効性を提供する|
|camera_http_bridge|生画像・認識画像・目標情報をPCへ提供する|
|autonomous_driving|座標から左右方向と相対的な近さを計算し、速度・操舵・停止要求を生成する|
|pc_bridge / motor_controller|PCで選んだ指令元に従ってモーターを制御し、PC停止・緊急停止を反映する|

ここでいう認識の「追跡」は画像内で点の移動を追うこと。
車両が点に向かって走る判断は自動走行ノードが担当し、認識ノードには左右の操舵判断を戻さない。

## 3. 画像取得と事前評価

1. 車両停止状態で、照射なし／ありの元JPEGを保存する。
2. 左・中央・右、水平線付近・中間・手前、静止・移動を記録する。
3. 照射位置のRGB値、赤成分の優位性、周辺との明暗差、点の面積を比較する。
4. 320×240で赤色や位置の情報が不足する場合は640×480・10fpsで比較する。
   解像度変更時は認識処理時間も測り、面積・探索半径を画像サイズに合わせて調整する。
5. 露出・ゲイン・ホワイトバランスは実機の対応設定を確認して比較する。
   認識のために必要な色を残せるかと、床面が暗くなりすぎないかを評価する。

しきい値・最低画素数はこの画像評価で決める。表示を拡大しても入力画像の情報は増えない。
照射前後の比較画像は調整・評価に使い、走行中の単純な画像差分を唯一の判定条件にはしない。

## 4. 検出条件

認識モード名の案を`red_laser_spot`とし、広い明部検出とは独立した設定を持つ。

- 探索範囲は画像下半分すべて。下1/4も検出を続け、緊急停止判定に必要な座標を提供する。
- RGBの赤成分優位性やHSVの赤色範囲から、周囲より赤い画素を探す。
  HSVの赤色範囲は色相の両端を扱い、彩度・明度も確認する。
- 明るさは絶対値だけでなく、小領域の周囲との局所コントラストを評価する。
- 明るい中心が白っぽい場合は、周囲の赤い縁と結び付くコンパクトな明部を同じ光点として扱う。
  赤い縁を伴わない白い反射を、新しいレーザー目標として選ばない。
- 微小な点を消さないよう、従来の12px以上の面積条件や3×3の中央値処理・収縮処理をそのまま流用しない。
  小領域の候補を残し、ノイズとの区別は赤色・局所コントラスト・時間方向の確認で行う。
- 大きな赤い物体、カーペット模様、孤立したノイズ、細長い反射を除外するため、面積・局所的なまとまりを確認する。
  微小な点では円形度が安定しないので、完全な円形を必須条件にしない。
- 画面境界で切れ、中心を安定算出できない候補は無効にする。

**白い点しか残らず赤色の根拠が取得できない場合、新規取得はUnknownとする。**
明るいという理由だけで追尾を開始せず、解像度・露出を見直して識別可能かを評価する。

## 5. 座標と画像内の追跡

- 座標は元画像の左上原点。xは右、yは下。ピクセル座標と0〜1の正規化座標を提供する。
- 光点中心は、周辺背景を引いた明るさ・赤成分による重み付き重心から求める。
  中心部が白っぽい場合は、赤い縁に対応付いた中心部も重心算出に含める。
- 新規目標は原則2枚以上の異なる入力stampで確認して確定する。
- 追跡中は前回位置・短時間の移動予測の近傍を優先し、位置、赤色、明暗差を照合する。
  誤った飛び移りを避けるため、急なジャンプは再確認する。
- 点の動きはライト操作だけでなく車両・カメラの動きも含む。予測位置だけで目標を確定しない。
- 同程度の複数候補があり、追跡履歴でも区別できない場合はambiguous、目標無効とする。
- 点が消えた／赤色の根拠が失われた／入力が古くなった場合は、現在の有効座標を返さない。
  内部で追跡履歴や予測を保持しても、予測だけの座標は走行用の有効目標にしない。
- 再取得時は確定条件を満たしてから有効に戻す。IDの保持・更新を結果に明示する。
- 平滑化で消失を隠さず、フィルターを入れた場合は追加される遅延も測る。

## 6. 結果と状態

既存の`/vision/ground_target`とHTTP `/target`の契約を維持する。

|項目|内容|
|---|---|
|mode|red_laser_spot|
|state|searching / confirming / tracking / ambiguous / lost / stale / error|
|target_valid|新しい実画像に基づいて光点を確定できた場合だけtrue|
|target.target_px|光点中心のピクセル座標|
|target.target_normalized|光点中心の正規化座標。自動走行が使用する|
|target.track_id|画像内の対応付けID|
|target.quality|赤色・局所コントラスト・対応付けの品質指標。正解率の確率ではない|
|target.ground|null。距離のメートル換算は未校正|
|source_frame|入力stamp・サイズ・frame_id・座標系|
|reason|赤成分不足、複数候補、点の消失、古い入力などの理由|

無効時は`target_valid=false`かつ`target=null`。
画像受領から300msを初期の有効期限として、送信側・受信側の両方で鮮度を確認する。
同じ画像の再配信や予測座標によって有効期限を延長しない。
現行の自動走行仕様の入力寿命1.5秒は、レーザー追尾では300msへ合わせる変更が必要。

## 7. 車両による追尾との接続

既存の自動走行の制御方針を引き継ぐ。

- 自動走行側がx座標から左右方向を算出する。認識側は座標を提供する。
- y座標から相対的な近さを計算し、水平線付近では速く、手前では遅くする。
  これは画像上の相対距離で、メートル単位の距離ではない。
- 目標中心が`y / 画像高さ >= 0.75`なら緊急停止を要求し、停止ラッチを保持する。
- Unknown、未確定、候補が曖昧、ロスト、期限切れは速度・操舵を0にする。
- 手動／自動はPCで選択する。PC停止・緊急停止・通信途絶時の停止を優先する。
- 緊急停止後のラッチ解除・再有効化を必要とする。通常の目標消失後の再開方針は既存自動走行仕様に従う。

## 8. PC確認表示と受け入れ試験

PCの画像中央には調整用の赤い水平線を表示し、レーザー候補は橙枠、確定目標は緑の印で区別する。
追跡ID、座標、認識状態、無効理由を表示する。
左右方向・相対距離・速度/操舵指令の表示値は自動走行側の結果を使う。
ブラウザーの`recognition: ok`だけではレーザーの追跡成立を示さない。

試験は録画・静止車両、走行dry-run、実車の順で行う。

1. 下半分の赤い照射点を左・中央・右で取得し、実際の中心との位置ずれを測る。
2. 小さい点、白っぽい中心、明るい部屋・暗い部屋、床模様・白い反射・赤い物体を比較する。
3. ゆっくりした移動・急な移動・一時消失・複数候補で追跡と無効化を確認する。
4. 上半分は追尾しない。下1/4の点は検出したうえで、自動走行が緊急停止することを確認する。
5. 入力停止・認識停止・通信断・古いフレームの再送で、無効化と停止を確認する。
6. カメラ配信・認識・PC表示・モーターdry-runを同時に動かし、実効fpsと遅延を測る。

評価には検出率、反射への誤検出率、座標誤差、再取得時間、ロストから停止までの時間を記録する。
光点の移動から結果が出るまでの応答と、JPEG受領後の処理時間を分ける。
100ms以内の応答は現時点では達成済みとせず、対象画像で実測して判断する。
